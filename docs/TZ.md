## 1. Продукт

### 1.1 Что это

Интерактивная модель, которая из одной экстраполяции (горизонт автономных задач METR) выводит два обратных отсчёта:

- **до сингулярности** — момента, когда ИИ обгоняет медианного профессионала в заданной доле видов деятельности;
- **до катастрофы** — по трёхуровневой шкале «локальный / региональный / глобальный».

Плюс рейтинг стран по AI-лидерству, панель наблюдаемых событий-триггеров и лента данных, которая обновляется сама.

### 1.2 Зачем

Ключевая мысль, которую сервис должен доносить конструкцией, а не текстом: **дата не является результатом — результатом является чувствительность даты к допущениям.** Пользователь двигает ползунок и видит, что глобальная катастрофа уехала на сорок лет. Из этого он должен сам сделать вывод, что спорить надо про допущение, а не про дату.

Поэтому в интерфейсе всегда рядом: число, ползунок, который его меняет, и источник, откуда взят дефолт.

### 1.3 Тон

Серьёзная модель, ироничная подача. Оформление в духе Часов Судного дня: тёмный терминал, сухие формулировки, самоирония в подписях и дисклеймерах. Никакого алармизма и никакого технооптимизма — сервис не занимает позицию, он даёт аппарат.

**Красные линии.** Сервис оперирует числами жертв. Это накладывает обязательства:

- нигде не даются персональные предсказания («вы умрёте в…»), геотаргетированные прогнозы или советы по выживанию;
- нигде не называются конкретные компании, лаборатории или страны как виновники будущих событий;
- сценарии в карточках катастроф описываются на уровне механизма («каскадный отказ энергосети»), без операционных деталей, которые кто-то мог бы прочитать как инструкцию;
- дисклеймер о непрогнозируемости — не в футере мелким шрифтом, а отдельным блоком в потоке страницы.

### 1.4 Целевая аудитория

Технически грамотная публика: инженеры, аналитики, журналисты, преподаватели. Человек, который умеет читать логарифмическую шкалу и которого раздражает, когда прогноз подают без интервала.

## 2. Расчётное ядро

Ядро — **чистый TypeScript-пакет без зависимостей и без обращений к DOM, сети и времени**. Оно принимает объект допущений и возвращает объект результатов. Это требование не обсуждается: ядро должно одинаково исполняться в браузере, в Node на сервере (для OG-картинок и предрасчёта) и в тестах.

Текущее время передаётся параметром `now: number`. Обращений к `Date.now()` внутри ядра быть не должно — иначе тесты не воспроизводимы.

### 2.1 Опорная точка

```
T0 = 2025-11-24        // релиз Claude Opus 4.5
H0 = 320               // 50%-горизонт METR, минуты
```

Опорная точка должна читаться из данных, а не быть зашита в код: при появлении новой модели с более высоким горизонтом якорь смещается на неё автоматически (см. 10.2).

### 2.2 Экстраполяция горизонта

```
D_эфф   = время_удвоения × трение × Π(множители активных триггеров)
H(t)    = H0 · 2^((t − T0) / D_эфф)
дата(H) = T0 + D_эфф · log₂(H / H0)
```

Множитель надёжности: при требовании 80% успеха вместо 50% требуемый горизонт умножается на 5 (METR: 80%-горизонт примерно впятеро короче 50%-го).

### 2.3 Даты по видам деятельности

Каждый элемент (вид мыслительной деятельности или отрасль) описан коэффициентом сложности `m` относительно программной инженерии и лагом внедрения `lag` в годах.

```
дата(элемент) = дата(m · порог_задачи · надёжность) + lag · множитель_группы
```

`множитель_группы` — влияние триггеров на группы `phys` (физический труд), `sci` (наука), `soc` (социальное). По умолчанию 1.

Прогресс для полосы:

```
p = (log₂(H(now)) − log₂(требуемый) + 12) / 12,     ограничить [0, 1]
если p ≥ 1 и lag > 0:
    p = 0.88 + 0.12 · доля_пройденного_лага
```

### 2.4 Дата сингулярности

Отсортировать даты всех элементов (виды деятельности + отрасли), взять перцентиль, заданный ползунком «порог сингулярности». Дефолт — 50-й, то есть медиана.

Это важное архитектурное решение: **головной счётчик не является отдельной формулой, он выводится из разбивки.** Так пользователь всегда может ткнуть в счётчик и увидеть, из чего он собран.

### 2.5 Интенсивность катастрофического риска

Для каждой из трёх ступеней:

```
c_i(t)  = 1 / (1 + exp(−0.8 · (log₂(H(t)) − log₂(порог_способности_i))))
d(t)    = dep₀ + (1 − dep₀) · (1 − exp(−max(0, t − now) / τ))
a_i(t)  = exp(−max(0, t − t_нас_i) / окно_уязвимости)
          где t_нас_i = дата(порог_способности_i · 8)

λ_i(t)  = (умысел · w_i + отказ_контроля · u_i) · c_i(t) · d(t)
          · (1 − митигация · e_i) · множитель_триггеров_i

P_i(t)  = 1 − exp(−Σ λ_i)      // интегрирование с шагом в год, 2026…2100
```

Медианная дата — линейная интерполяция года, в котором `P` пересекает 0,5. Если не пересекает — возвращать `null`, интерфейс показывает «за пределами модели».

Вероятность события любого уровня: `1 − Π(1 − P_i)`.

`a_i(t)` — реализация идеи «времени опасностей»: риск не копится вечно, после насыщения способностей мир адаптируется. Без этого множителя любая кривая уходит в 100% и модель становится бессодержательной.

### 2.6 Производные величины

- **Ожидаемые жертвы и ущерб к году X:** `Σ P_i(X) · √(нижняя_i · верхняя_i)` — геометрическое среднее диапазона.
- **Часы Судного дня:** `минут_до_полуночи = max(0.2, 15 · (1 − P_глобальный(2100)))`.
- **Уровень тревоги** (для бейджа): `<5%` спокойно, `<15%` настороженно, `<35%` серьёзно, иначе критично.

### 2.7 Требования к тестам ядра

Обязательны golden-тесты: зафиксировать выход ядра на всех пресетах при фиксированном `now` и сравнивать побайтово. Любое изменение констант должно ломать тест — это фича, а не баг: изменение допущений обязано быть осознанным.

Дополнительно:

- монотонность: увеличение `отказ_контроля` не должно отодвигать глобальную дату, увеличение `митигация` не должно приближать;
- отсутствие `NaN` и `Infinity` на всех крайних положениях всех ползунков (перебором);
- `P` не убывает по годам, лежит в [0, 1];
- при `умысел = 0` и `отказ_контроля = 0` все `P` равны нулю.

## 3. Раздел «Сингулярность»

Определение операциональное и должно быть проговорено в интерфейсе: сингулярность наступила, когда ИИ выполняет самостоятельно, без человека в цикле, задачу заданной длины в заданной доле видов деятельности. Никакого «пробуждения сознания».

**Управление:** время удвоения (60–300 дней), трение реального мира (0,5–4,0), порог задачи (день / неделя / месяц / год), требуемая надёжность (50% / 80%), порог сингулярности (10–95%).

**График экстраполяции.** Логарифмическая шкала по вертикали, время по горизонтали. Точки METR, линия по текущему допущению, пунктир после сегодняшнего дня, горизонтальные линии порогов, маркер на дате достижения выбранного порога. Обязательна подпись, что линия закреплена в последней точке, а не подогнана под историю — иначе расхождение с ранними точками читается как ошибка.

**Две таблицы-списка:** 12 видов мыслительной деятельности и 18 отраслей. Каждая строка: название, пояснение, полоса прогресса, дата обгона. Пройденные подсвечены зелёным с годом. Сортировка по дате.

Строки должны быть кликабельны: раскрывается панель с коэффициентом сложности, лагом, обоснованием и — если есть — ссылкой на источник, откуда взята оценка.

## 5. Панель триггеров

Список наблюдаемых событий, каждое с описанием, уточнением критерия («не разовый джейлбрейк пользователем, а инициатива системы») и явным указанием эффекта на модель. Отмечаются галочками, эффект применяется немедленно.

Триггеры делятся на **разгоняющие** (красная рамка) и **успокаивающие** (зелёная рамка). Второй тип обязателен: без него панель превращается в машину нагнетания.

**Расширение относительно прототипа:** каждый триггер связан с лентой событий (раздел 7). Если система нашла в источниках событие, похожее на триггер, рядом появляется бейдж «возможно, произошло» со ссылкой на первоисточник и датой. Автоматически триггер не включается никогда — решение всегда за пользователем.

## 6. Рейтинг стран

Отдельный раздел, а не отдельный сайт: рейтинг должен быть связан с основной моделью, иначе это просто ещё одна табличка.

### 6.1 Методика

Семь компонентов, каждый нормируется в 0–100 (min-max по выборке стран, с фиксацией шкалы между обновлениями):

| Компонент | Что измеряет |
|---|---|
| Исследования | публикации, цитируемость, доля на топ-конференциях |
| Патенты и интеллектуальная собственность | заявки, гранты, доля в мировом объёме |
| Талант | численность исследователей, приток и отток |
| Инфраструктура | доступный компьют, дата-центры, доступ к передовым чипам |
| Инвестиции | частные и государственные вложения, число сделок |
| Коммерциализация | компании, выручка, проникновение в экономику |
| Управление и регулирование | зрелость регулирования, институты оценки, участие в договорах |

Итог — взвешенная сумма. **Веса настраиваются пользователем**, дефолт равновесный. Обязательна кнопка «показать, как менялся рейтинг при других весах» — потому что вся содержательная разница между публичными индексами AI-лидерства сводится к весам, и сервис должен это показать, а не спрятать.

### 6.2 Связь с основной моделью

Не декоративная. Из рейтинга считается **индекс гонки**: концентрация лидерства по Херфиндалю–Хиршману на топ-5 странах.

```
HHI = Σ (доля_i)²   по нормированным баллам топ-5
индекс_гонки = 1 − нормированный_HHI
```

Чем ровнее гонка, тем труднее договориться и тем ниже потолок эффективности митигации. По умолчанию связь **выключена**, с переключателем «учитывать геополитику в модели риска». Когда включена:

```
митигация_эфф = митигация · (1 − 0.4 · индекс_гонки)
```

Коэффициент 0,4 вынести в конфиг. Обязательно пояснение, что это допущение автора модели, а не установленный факт.

### 6.3 Визуализация

Таблица с сортировкой по любому компоненту, горизонтальные полосы разбивки по компонентам для выбранной страны, режим сравнения двух стран. Картограмма — опционально и последней в очереди: она красивая, но менее информативная, чем таблица.

## 7. Живая лента событий и автообновление

Раздел, ради которого нужен бэкенд.

### 7.1 Источники

| Источник | Что берём | Как | Частота |
|---|---|---|---|
| METR | новые точки горизонта, публикации методики | парсинг страницы `metr.org/time-horizons` + блог | ежедневно |
| AI Incident Database | новые инциденты, категории, тяжесть | публичные выгрузки/API | ежедневно |
| Metaculus | котировки по вопросам об AGI и катастрофах | публичный API | ежечасно |
| Manifold Markets | то же | публичный API | ежечасно |
| Epoch AI | данные по вычислениям, размерам моделей | публичные датасеты | еженедельно |
| Stanford HAI AI Index | компоненты странового рейтинга | годовой отчёт, ручная сверка | при выходе |
| OECD.AI Index | компоненты странового рейтинга | публикации | при выходе |
| Tortoise Global AI Index | компоненты странового рейтинга | публикация | при выходе |
| arXiv | препринты по оценкам способностей и безопасности | API по категориям | ежедневно |

**Правила работы с источниками, обязательные к соблюдению:**

- уважать `robots.txt` и условия использования каждого источника; где есть API — использовать API, не парсинг;
- разумный rate limit и `User-Agent` с контактом;
- кэшировать агрессивно, никогда не ходить в источник из пользовательского запроса — только из фонового задания;
- сохранять исходный ответ (raw) вместе с нормализованным — чтобы можно было пересчитать при изменении парсера;
- при недоступности источника показывать последнее известное значение с датой и пометкой «данные устарели», а не пустоту и не ошибку.

### 7.2 Модерация

Ничто из автоматически собранного не попадает в модель само. Пайплайн: собрали → нормализовали → классифицировали (относится ли к какому-то триггеру) → положили в очередь `pending` → человек подтвердил → опубликовали в ленту как «возможное срабатывание триггера».

Классификация может использовать LLM, но её вердикт — это подсказка модератору, а не решение. В интерфейсе всегда видно, что это предположение и по какому первоисточнику.

### 7.3 Отображение

Хронологическая лента: дата, источник со ссылкой, суть в одну строку, привязка к триггеру, если есть. Фильтр по типу. RSS-выдача ленты — обязательна, это дешёвый канал возврата пользователей.

## 8. Шаринг и сравнение сценариев

### 8.1 Сценарий

Полный набор допущений + состояние триггеров + веса рейтинга стран. Сериализуется двумя способами:

- **в URL** — компактная кодировка в query-параметр, работает без бэкенда и не протухает;
- **в короткую ссылку** — запись в БД, slug из 8 символов, для соцсетей и мессенджеров.

Оба должны работать. URL-кодировка — источник истины, короткая ссылка её лишь хранит.

### 8.2 OG-картинка

Генерируется на сервере по параметрам сценария: два счётчика, часы, название пресета, если совпал. Кэшируется по хешу сценария. Это главный канал распространения — не экономить на нём.

### 8.3 Режим сравнения

`?a=<сценарий>&b=<сценарий>` — два столбца с одинаковой структурой, различающиеся значения подсвечены. Графики накладываются друг на друга: сплошная и пунктирная линии одного цвета в паре, не разные цвета.

Пресеты («Базовый», «Оптимист», «Скептик», «Тревожный», «Судный день») — это просто именованные сценарии в той же системе, отдельного механизма для них не нужно.

### 8.4 Голосование по триггерам

Пользователь может отметить, считает ли он триггер уже сработавшим. Агрегат показывается рядом: «43% посетителей считают, что это уже произошло». Одно голосование на устройство, без регистрации, без сбора персональных данных. Это единственная форма пользовательского контента — комментариев не делать.

## 9. Архитектура

### 9.1 Требования, а не выбор

Стек выбирает разработчик, но решение должно удовлетворять:

- **типизация** — статическая, сквозная, включая контракты API;
- **SSR или пререндер** — обязателен для OG-картинок и индексации;
- **фоновые задания** — планировщик для сбора данных, отдельно от веб-процесса;
- **хранилище** — реляционное, с миграциями в репозитории;
- **деплой** — из main, автоматически, с превью-окружением на pull request;
- **стоимость простоя** — сервис должен жить на бесплатном или околобесплатном тарифе при нулевом трафике.

Выбор стека зафиксировать в `docs/adr/0001-stack.md` с обоснованием и отвергнутыми альтернативами.

### 9.2 Структура

```
packages/
  core/          — расчётное ядро, чистый TS, ноль зависимостей
  data/          — схемы, парсеры источников, нормализация
  ui/            — переиспользуемые компоненты, дизайн-токены
apps/
  web/           — сайт
  worker/        — фоновые задания сбора данных
reference/
  prototype.html — эталон формул
docs/
  adr/           — архитектурные решения
  model.md       — описание модели для людей
```

Границы жёсткие: `core` не знает про `data`, `data` не знает про `ui`. Проверять линтером на импорты.

### 9.3 Схема данных

Минимально необходимое:

- `sources` — реестр источников, статус, время последнего успешного опроса;
- `raw_fetches` — сырые ответы с хешем и временем;
- `metr_points` — точки горизонта: модель, дата, значение, методика, доверительный интервал, источник;
- `incidents` — нормализованные инциденты;
- `market_quotes` — котировки прогнозных рынков: площадка, вопрос, значение, время;
- `country_metrics` — страна, компонент, год, значение, источник;
- `feed_items` — элементы ленты, статус модерации, связь с триггером;
- `scenarios` — короткие ссылки: slug, сценарий, время создания;
- `trigger_votes` — голоса, хеш устройства, триггер, значение.

Все таблицы с данными из внешних источников обязаны хранить ссылку на первоисточник. Число без источника в этом сервисе не имеет права на существование.

### 9.4 API

Публичный, read-only, документированный, с CORS:

```
GET  /api/model/defaults       — текущие дефолты и опорные точки
GET  /api/metr/points          — исторические точки горизонта
GET  /api/countries?year=      — рейтинг стран с разбивкой
GET  /api/feed?since=&type=    — лента событий
GET  /api/markets              — сводка прогнозных рынков
POST /api/scenario             — создать короткую ссылку
GET  /api/scenario/:slug       — прочитать сценарий
POST /api/vote                 — голос по триггеру
GET  /api/og?s=<сценарий>      — OG-картинка
```

Расчёт модели через API **не выставлять** — он делается на клиенте, это принципиально: сервис должен полностью работать при отвалившемся бэкенде, деградируя до последних закэшированных данных.

## 10. Данные и их жизненный цикл

### 10.1 Разделение

- **Константы модели** (коэффициенты сложности, лаги, веса триггеров, параметры ступеней) — экспертные суждения, живут в репозитории в виде версионированного YAML/JSON, меняются через pull request с обоснованием в описании.
- **Измеряемые данные** (точки METR, инциденты, котировки, страновые метрики) — живут в БД, обновляются автоматически.

Смешивать нельзя. В интерфейсе они тоже должны различаться визуально: измеренное и предположенное подаются по-разному.

### 10.2 Автоматическое смещение якоря

При появлении точки METR с горизонтом выше текущего якоря — якорь смещается на неё, все даты пересчитываются. Событие попадает в ленту отдельным элементом: «якорь модели смещён, все прогнозы сдвинулись на N дней».

Это, вероятно, самая эффектная механика всего сервиса. Реализовать аккуратно и показывать заметно.

### 10.3 Провенанс

У каждого числа в интерфейсе, полученного из данных, при наведении показывается: источник, дата получения, ссылка. У каждого числа, являющегося допущением, — пометка «оценка» и ссылка на обоснование в `docs/model.md`.

## 11. Дизайн

### 11.1 Основа

Тёмная тема как основная. Светлая — опционально, и если делается, то отдельно подобранными значениями, а не автоматической инверсией.

Палитра прототипа проверена на цветовую слепоту и контраст, взять её:

```
поверхность      #1a1a19      фон страницы    #0d0d0d
основной текст   #ffffff      вторичный       #c3c2b7      приглушённый #898781
сетка            #2c2c2a      оси             #383835
серия 1 (синий)  #3987e5
ступени риска (порядковая шкала, один тон):
  локальный #184f95 · региональный #3987e5 · глобальный #86b6ef
статусы: норма #0ca30c · внимание #fab219 · серьёзно #ec835a · критично #d03b3b
```

Шрифт — системный без засечек, включая крупные числа. Табличные цифры для тикающих счётчиков, иначе они дёргаются.

### 11.2 Правила графиков

- Порядковые шкалы (три ступени риска) — один тон, разная светлота, плюс различающийся штрих; никогда не «жёлтый-оранжевый-красный» подряд, эта тройка неразличима при дейтеранопии.
- Никогда не две оси Y на одном графике.
- Цвет закреплён за сущностью, а не за позицией в списке: фильтр не должен перекрашивать оставшиеся серии.
- Текст подписей — цветами текста, не цветом серии; идентичность несёт плашка рядом.
- Легенда обязательна при двух и более сериях, прямые подписи в конце линий — дополнительно.
- Всплывающая подсказка при наведении — на всех графиках по умолчанию, не по запросу.
- У каждого графика есть режим просмотра таблицей.

### 11.3 Адаптивность

Мобильная версия обязательна: значительная доля переходов будет из мессенджеров. На узком экране счётчики в столбец, ползунки полной ширины, графики с горизонтальной прокруткой или упрощённые.

## 12. Локализация

Русский и английский с первого дня, архитектурно — с возможностью добавить третий без переписывания.

Особенности:

- числа и даты форматируются по локали (в русском — запятая как десятичный разделитель, это в прототипе уже учтено);
- склонения числительных в русском («1 год / 2 года / 5 лет») — через правила множественного числа, а не через `if`;
- тексты триггеров, сценариев и пояснений — существенная часть продукта; переводить их машинно нельзя, нужна человеческая редактура;
- язык определяется по домену или префиксу пути, не по заголовку браузера, — чтобы ссылка вела туда, куда её отправили.

## 13. Нефункциональные требования

**Производительность.** Пересчёт модели при движении ползунка — не более 16 мс, чтобы попадать в кадр. Считать синхронно на главном потоке; если не укладываемся — выносить в Web Worker с дебаунсом, но сначала измерить, а не оптимизировать вслепую. Первая отрисовка — под секунду на среднем мобильном соединении.

**Доступность.** Клавиатурная навигация по всем ползункам и переключателям, ARIA-разметка графиков с текстовой альтернативой, контраст не ниже 4,5:1 для текста и 3:1 для графических элементов, уважение `prefers-reduced-motion` (пульсация счётчика отключается).

**SEO.** Серверный рендер, осмысленные заголовки и описания, структурированная разметка, sitemap. Отдельные индексируемые страницы для каждого пресета и для рейтинга стран.

**Приватность.** Без учётных записей, без cookie-баннера, потому что без cookies. Аналитика — только не требующая согласия и без персональных данных, либо никакой. Голоса по триггерам — по хешу устройства, не по идентификатору пользователя. В политике конфиденциальности честно написать, что именно хранится.

**Наблюдаемость.** Логи заданий сбора данных с результатом по каждому источнику. Оповещение, если источник недоступен более суток. Публичная страница статуса данных: когда какой источник опрашивался последний раз и что вернул. Прозрачность здесь — часть продукта, а не служебная функция.

**Лицензия.** Код — открытый (MIT или Apache 2.0). Константы модели и тексты — CC BY. Открытость здесь принципиальна: модель, чьи допущения нельзя посмотреть, не имеет права претендовать на серьёзность.

## 14. Чего делать не надо

Явные анти-требования, чтобы не потратить время впустую:

- не делать регистрацию, профили, подписки, платные тарифы;
- не делать комментарии и любую переписку между пользователями;
- не делать чат с ИИ внутри сервиса — это не то, чего от него ждут;
- не делать push-уведомления «до конца света осталось…» — это ровно та грань, за которой ирония становится безвкусицей;
- не добавлять новые виды деятельности и отрасли сверх списка без обоснования: тридцать позиций — это уже много для восприятия;
- не усложнять модель ради реализма. Если множитель нельзя объяснить в одном предложении, он в модели не нужен.

## 15. Этапы

### M0 — каркас

Репозиторий, структура пакетов, выбор стека с ADR, CI (линтер, типы, тесты), пустой деплой.
**Готово, когда:** пустая страница задеплоена, CI зелёный, ADR написан.

### M1 — ядро и первый экран

Пакет `core` целиком по разделу 2. Golden-тесты. Два счётчика, часы, пресеты, оба набора ползунков.
**Готово, когда:** значения при всех пресетах совпадают с прототипом; на крайних положениях всех ползунков нет `NaN`; счётчик тикает и не дёргается.

### M2 — графики и разбивки

График экстраполяции, график накопленной вероятности, две таблицы-списка, карточки ступеней, панель триггеров, блок математического ожидания.
**Готово, когда:** все графики имеют подсказку при наведении и режим таблицы; полностью работает с клавиатуры; проходит проверку контраста.

### M3 — шаринг

Кодировка сценария в URL, короткие ссылки, OG-картинка, режим сравнения.
**Готово, когда:** ссылка, открытая в чистом браузере, воспроизводит сценарий в точности; предпросмотр корректно отображается в Telegram, X и Slack.

### M4 — данные

Бэкенд, схема, воркер, сбор из источников по разделу 7, страница статуса данных, лента с модерацией, автоматическое смещение якоря.
**Готово, когда:** сутки работы воркера без ручного вмешательства; при выключенном бэкенде фронтенд полностью функционален на закэшированных данных.

### M5 — рейтинг стран и локализация

Раздел рейтинга, настраиваемые веса, индекс гонки и связь с моделью, английская версия.
**Готово, когда:** обе локали полны, тексты вычитаны человеком, склонения числительных корректны.

**Порядок фиксирован.** M1 не начинать до M0, M4 не начинать до M3. Соблазн сделать сначала красивый график и потом под него подгонять модель — главная ловушка этого проекта.

# ADR-0001. Выбор стека: статика первой, бэкенд потом

**Статус:** принято 2026-08-17
**Контекст:** требования раздела 9.1 ТЗ, решение владельца продукта отложить
бэкенд до появления работающей модели.

## Решение

**V0 — сайт без сервера состояния.** Ни базы данных, ни воркера сбора, ни
модерации. Единственный серверный код — одна функция без состояния, рисующая
OG-картинку из параметров URL.

| Слой | Выбор |
|---|---|
| Язык | TypeScript, `strict`, единая версия на монорепозиторий |
| Монорепозиторий | pnpm workspaces, задачи через `pnpm -r` |
| Сайт | Astro 5, острова на React 19, пререндер всех страниц |
| Хостинг | Cloudflare Workers со статическими ассетами |
| OG-картинки | одна edge-функция, Satori + resvg-wasm, без состояния |
| Данные | версионированные YAML/CSV в репозитории |
| Графики | рукописный SVG, без библиотек |
| Тесты | Vitest, fast-check, Playwright + axe |
| CI | GitHub Actions, превью-деплой на PR |

## Что это меняет в объёме V0

Отсутствие бэкенда режет из ТЗ ровно три вещи, и все три — периферийные:

| Функция ТЗ | Судьба в V0 | Почему не больно |
|---|---|---|
| Короткие ссылки (§8.1) | **убрана** | Кодек даёт ~30 символов в query. Это влезает в Telegram, X и Slack без переносов. Короткая ссылка была удобством, а не механизмом. |
| Голосование по триггерам (§8.4) | **убрана** | Требует хранилища и защиты от накрутки. Единственная форма пользовательского контента — без неё сервис не теряет смысла. |
| Живая лента и автосмещение якоря (§7, §10.2) | **отложена до M4** | Самая эффектная механика проекта, но она бессмысленна, пока нет модели, к которой её прикручивать. |

Всё остальное из ТЗ работает на статике, в том числе то, чего не ожидаешь:

* **Рейтинг стран целиком.** Данные HAI, OECD и Tortoise всё равно не
  машиночитаемы (см. `docs/architecture.md` §3.4) — в V0 это выверенный вручную
  CSV в репозитории с колонкой источника на каждую ячейку. Настраиваемые веса,
  индекс гонки и связь с митигацией считаются на клиенте.
* **Точки METR.** Тот же YAML. Смещение якоря в V0 — pull request, а не
  автоматика. Механика та же, спусковой крючок ручной.
* **Обе локали, все пресеты, режим сравнения, OG-картинки.**

Итог: V0 — законченный продукт, а не демо. Отложено то, что делает его живым,
а не то, что делает его работающим.

## Обоснование выбора

**Astro.** Сайт неоднороден: главная — один большой интерактивный остров, а
рейтинг, документация модели, пять страниц пресетов и обе локали — статика,
которой нужен SEO. Astro отдаёт статику статикой и грузит JS только под остров.

Ключевое: ядро — чистый TypeScript, поэтому Astro считает модель **на этапе
сборки** и отдаёт готовый HTML с посчитанными счётчиками и нарисованными SVG.
Гидратация только оживляет ползунки. Для страницы-калькулятора это единственный
способ уложиться в «первая отрисовка под секунду на среднем мобильном».

**Cloudflare Workers со статическими ассетами.** Ноль стоимости простоя без
звёздочек, превью на PR, и — важное на будущее — Cron Triggers на бесплатном
плане. Когда дойдём до M4, ежечасный опрос прогнозных рынков не потребует
менять хостинг. На бесплатном Vercel планировщик умеет только два ежедневных
задания, и M4 упёрся бы в переезд или во внешний пингер.

**OG отдельной функцией без состояния.** Satori + resvg-wasm + TTF с кириллицей
— около мегабайта бандла. Отдельный воркер изолирует и размер, и холодный старт.
Функция чистая: URL-параметры → PNG, никакого чтения данных. Ключ кэша —
`hash(байты_сценария ‖ версия_конфига)`; версия конфига обязательна, иначе после
первой же правки констант в мессенджерах навсегда застынет старая картинка.

**Графики руками.** Требования §11.2 и §13 — режим таблицы, клавиатурная
подсказка, цвет за сущностью, серверный рендер SVG — это список того, что в
библиотеках приходится обходить. В прототипе оба графика занимают ~120 строк
генерации SVG; переносим их в React-компоненты и экономим 50–150 КБ на странице,
где важна первая отрисовка.

## Отвергнутые альтернативы

**Полный стек с БД сразу** (Astro + D1 + Drizzle + воркер сбора). Отвергнут
владельцем продукта в пользу более быстрого выхода на работающую модель. Решение
здравое: главная ловушка этого проекта — построить красивую обвязку вокруг
непроверенного ядра. Архитектура спроектирована так, что добавление бэкенда в M4
не требует переписывания: ядро уже принимает конфиг параметром, а не читает его.

**Next.js на Vercel.** Лучшая генерация OG из коробки и знакомый всем App
Router. Отвергнут из-за планировщика на бесплатном тарифе, который заблокирует
M4, и из-за тяжёлого клиентского рантайма на странице, которая на 80% статична.

**SvelteKit.** Меньше бандл, тот же хостинг. Отвергнут по нетехнической причине:
React-острова проще передать следующему разработчику и проще отдать агенту.

**SPA на Vite + React.** Нет SSR — нет ни OG, ни индексации, ни быстрой первой
отрисовки. Отпадает по §9.1.

**Turborepo.** Был в первой редакции этого ADR и выброшен при сборке каркаса:
`pnpm -r` и так исполняет задачи в топологическом порядке, а внутренние пакеты
экспортируют TypeScript напрямую и вовсе не собираются. Turbo дал бы кеш на
шести пакетах, где полная проверка занимает секунды. Лишний инструмент против
антитребования §14 не устоял.

**Полностью статический сайт вообще без серверных функций.** Тогда OG-картинка
для произвольного сценария невозможна: краулеры мессенджеров не исполняют JS, а
предгенерировать все сценарии нельзя — их 10²⁰. Пришлось бы отдавать одну
картинку на все ссылки, то есть похоронить главный канал распространения ради
экономии одной чистой функции. Не стоит того.

## Последствия

* Пока нет БД, `packages/data` — это схемы плюс статические датасеты. Парсеры
  источников появляются в M4 и кладутся туда же.
* Дата последней сверки данных должна быть на видном месте на каждой странице с
  числами: ручное обновление тем честнее, чем виднее его давность.
* Привязка к Cloudflare касается только `apps/*`. Пакеты `core`, `data`, `ui`
  остаются платформенно-нейтральными, что проверяется линтером.

## Что проверить перед началом M0

Платформа Cloudflare меняется быстро. До первой строки кода проверить по
актуальной документации: превью-деплой на PR для Workers со статическими
ассетами (запасной вариант — Cloudflare Pages), лимит размера воркера на
бесплатном плане и совместимость `@astrojs/cloudflare` с текущей версией Astro.

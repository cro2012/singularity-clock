# ADR-0004. Хостинг: Netlify. Отменяет выбор Cloudflare из ADR-0001

**Статус:** принято 2026-08-17. Отменяет раздел о хостинге в
[ADR-0001](0001-stack.md); остальная часть ADR-0001 (Astro, статика первой,
TypeScript, рукописные графики) в силе.

## Почему пересматриваем

ADR-0001 выбирал хостинг так, как будто инфраструктуры нет вовсе. Она есть:

| Что уже есть | Где используется |
|---|---|
| **Netlify** — git auto-deploy, самоуправляемый | `custovault.com`, лендинг деплоится push в `main` |
| **Hetzner GEX44** — выделенный сервер, схема «спайн + ячейки» | пилот Custovault, ячейки `demo`, `tickerpicker` |
| **Porkbun** — регистратор и DNS | `custovault.com`, `custovault.eu` |

Заводить третьего провайдера ради проекта, который в V0 представляет собой
статический бандл плюс одну функцию без состояния, нечем оправдать.

## Решение

**Netlify.** Сайт — статика из `apps/web/dist`, OG-картинки — Netlify Function.

| Требование ТЗ §9.1 | Как закрывается |
|---|---|
| SSR или пререндер | пререндер на сборке, как и было |
| деплой из `main` автоматически | git auto-deploy, уже настроенный рабочий процесс |
| превью-окружение на PR | Deploy Previews, из коробки |
| стоимость простоя | бесплатный тариф покрывает проект целиком |
| фоновые задания (M4) | Scheduled Functions, синтаксис cron, ежечасно доступно |

Побочная выгода, которой у Cloudflare не было: OG-функция исполняется в Node,
а не в воркере. Satori с растеризацией на нативном биндинге в Node проще и
надёжнее, чем resvg-wasm под лимитом размера воркера — ADR-0001 отводил под
этот риск отдельный деплой-юнит, и он больше не нужен.

## Почему не Hetzner

Сервер оплачен и на нём есть готовая схема для стороннего приложения — казалось
бы, идеальный кандидат. Против три довода, и все три не технические:

1. **Радиус поражения.** На боксе лежат данные пилотного клиента (экспорт
   PRISM). Публичный полушуточный сайт про катастрофы рядом с ними — плохая
   идея независимо от того, насколько хорошо изолированы ячейки.
2. **Всплески трафика.** Распространение через OG-картинки в мессенджерах — это
   заявленный основной канал. Всплеск на боксе, обслуживающем платящего
   клиента, — ровно то, чего там быть не должно.
3. **Бэкапы на боксе не настроены** (CUS-47) и в собственной документации
   помечены как жёсткий блокер для реальных тенантов. Добавлять туда ещё один
   сервис до закрытия этого пункта — расширять проблему.

Статика на CDN всего этого не имеет по построению.

## Что меняется в репозитории

* `apps/web/wrangler.jsonc` → `netlify.toml` в корне;
* `apps/og` (отдельный воркер) → `apps/web/netlify/functions/og.mts`;
  отдельный деплой-юнит больше не нужен, деплой-юнитов остаётся один;
* `.github/workflows/deploy.yml` удаляется: деплоем занимается Netlify, а не
  GitHub Actions. CI остаётся и проверяет то же, что проверял.

## Починенный дефект: OG-функция падала на проде

Сайт опубликован 2026-08-18, все страницы отдавались, но `/og` отвечал 502:

```
TypeError: D.handler is not a function
```

Рантайм искал `exports.handler`, то есть считал функцию первым поколением,
хотя она написана через `export default` с `Request`/`Response`.

Пробные функции на том же конфиге локализовали причину:

| Проба | Результат |
|---|---|
| `export default` без импортов | 200 |
| `import satori from 'satori'` | 200 |
| `import sharp from 'sharp'` | 200 |
| `import { computeModel } from '@sc/core'` | **502, та же ошибка** |
| `import { parseModelConfig } from '@sc/data'` | **502, `Cannot find package 'yaml'`** |

Ломались импорты рабочих пакетов, а не платформа. Пакеты `packages/*` отдают
сырой TypeScript (`"exports": { ".": "./src/index.ts" }`). Vite это
разворачивает, потому что транспилирует весь граф; сборщик функций Netlify так
не умеет — он транспилирует файл функции на месте и трассирует зависимости как
обычные пакеты. Модуль падал при загрузке, и рантайм откатывался к поиску
`exports.handler`. Отсюда и вводящее в заблуждение сообщение: настоящая ошибка
была не в сигнатуре функции, а в том, что модуль вообще не загрузился.

**Решение (2026-08-18):** свой шаг сборки
`apps/web/scripts/build-functions.mjs`. esbuild собирает функцию со всеми
пакетами в один `.mjs` в `apps/web/netlify/dist-functions`, и `netlify.toml`
указывает на этот каталог, а не на исходники. Снаружи остаётся только `sharp`
— нативный биндинг, доезжает через `external_node_modules`.

Две вещи, найденные при сборке и стоящие того, чтобы их не переоткрывать:

* `yaml` — CommonJS, и в ESM-выводе esbuild его внутренний `require` падает на
  «Dynamic require of "process" is not supported». Лечится баннером с
  `createRequire`.
* Скрипт после сборки импортирует получившийся `.mjs` в чистом процессе Node и
  рендерит картинку. Обе проблемы всплыли именно там, а не на проде: бандл,
  который не грузится, обязан ронять сборку, а не отдавать 502.

## Последствия

* Привязка к платформе сместилась с Cloudflare на Netlify, но осталась в тех же
  границах: только `apps/*`. Пакеты `core`, `data`, `i18n`, `ui` платформенно
  нейтральны, и это проверяется линтером.
* Для M4 понадобится база. Netlify её не даёт. Решать в M4; кандидаты —
  Neon, Turso или Postgres на том же Hetzner-боксе, доступный только фоновому
  заданию, без публичного трафика на бокс. Последний вариант снимает довод 2 из
  предыдущего раздела, потому что публичный трафик остаётся на CDN.
